# ghidra-fmt-btree porting notes

Source: `db.NodeMgr` (node type table), `LongKeyNode`, `LongKeyInteriorNode`,
`LongKeyRecordNode`, `VarRecNode`, `FixedRecNode`.

## Status

| Node type | Java class | Status |
| --- | --- | --- |
| 0 | `LongKeyInteriorNode` | read path done |
| 1 | `VarRecNode` | read path done (direct and indirect records) |
| 2 | `FixedRecNode` | read path done (record length supplied by the caller) |
| 3, 4 | `VarKeyInteriorNode`, `VarKeyRecordNode` | NOT ported: they need the Field key encoding and ordering (layer L3). Opening returns `UnsupportedNodeType` |
| 5, 6, 7 | `FixedKey*` | NOT ported, same reason |
| 8, 9 | chained buffer nodes | in `ghidra-fmt-chain` |

The write path (insert, delete, split, merge, rebalance) is NOT ported. Java has no JUnit test
for nodes in isolation; they are exercised through `DBLongKeyTableTest` and friends, which need
the `Table`/`Schema`/`DBRecord` layer. So there is no one-to-one test port at this level.

## Tests

* `src/longkey/tests.rs`: hand-laid-out trees (from the layout documentation, not from the code
  under test): get, ordered scan, two levels, indirect record through a real chained buffer, fixed
  records, the `isConsistent` port detecting bad links and keys, unsupported/unexpected node
  types, corrupt nodes (negative or huge counts, bad offsets, empty interior, child loop, leaf loop).
* Fixture walk: every long-key table of both legacy fixtures is walked; record counts match the
  master table RECORD_COUNT, max keys match, consistency is clean.
* `tests/oracle_diff.rs`: differential check against the Java oracle, see below.

## Differential check

`oracle/Oracle.java` (package `db.buffers`, so it can reach `DataBuffer.data`) opens a `.gbf`
with `LocalBufferFile` and `DBHandle` and prints: geometry, free list, parameters, one line per
buffer (id, empty flag, SHA-256 of the payload), one line per table (name, record count and max
key as `Table` reports them), and the database id. `testdata/oracle-*.txt` are its outputs for
the two legacy fixtures. They were generated by compiling this repository's
`Framework/{Generic,Utility,DB,...}` sources with `javac -sourcepath` against the log4j and
commons jars of a stock Ghidra 12.2 install (the repository has no Gradle build output).

Result: every buffer of both fixtures is hash-identical, and all table names, record counts, max
keys and the database id are equal.

To regenerate: compile `oracle/Oracle.java` the same way, copy a fixture `db.1.gbf` somewhere,
run `java -cp <out>;<jars> db.buffers.Oracle <copy> > testdata/oracle-<name>.txt`.

## Behaviours kept from Java

* Interior search is `getIdIndex`: binary search starting at index 1, returning `max`.
* `isRightmostKey` asks the parent about this node first key, not the searched key.
* Var-record length is derived from neighbouring offsets (record 0 ends at the buffer end).
* The master table row carries `MAX_KEY`; index tables reuse the primary table name
  (`COLUMN_INDEXED != -1`), so name-keyed maps must filter on it.

## Deliberate differences

* Depth and leaf-chain loops are bounded (`TooDeep`) where Java would recurse or spin.
* Negative key counts and out-of-range offsets return `CorruptNode`/`Bytes` errors.
